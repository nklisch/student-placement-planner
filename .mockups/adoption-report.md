## Interaction paths reviewed

- Blank project → sample data → Find placements → results.
- Roster edits → another page's edits → Undo.
- CSV replacement/addition → validation → readiness.
- Address edit → retained coordinates → travel review.
- Solved result → changed input → stale export/print.
- Failed solve → result statistics/export controls.
- Download page → warning guidance → README/interface-guide links.

## Design-system observations

The application already has a shared light/dark token layer, native Qt controls, common banners/cards, and table models. Rebuilding that system is not the recommended response. The strongest findings concern input state, repair, misleading result states, and dark-mode primary-text contrast rather than stylistic fragmentation.

## Mocking and accessibility decisions

- No new mockups or speculative future screens: direct reproductions establish the defects more effectively.
- The smaller-window capture is the alternate-layout stress case for this pass. Native assistive-technology and OS scaling checks remain unverified, not presumed successful.
- Screenshots contain only synthetic/sample application content and were generated by Qt offscreen on Linux. No full-desktop screenshots were retained.
- Preserve the approved absences: no forced onboarding, accounts, map canvas, dashboard, or automatic roster persistence. The audit does not propose adding them.

Recheck the affected surfaces after their fixes, then walk a first-time user through download → imperfect CSV → repair → solve → save/reopen → export on each supported OS. No recurring design-review campaign is proposed.
